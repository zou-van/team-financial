# 研发过程 Loop

每个开发需求都按下面的顺序推进：

```text
inbox → spec → planned → building → verifying → review → done
```

流程配置位于 `config.yaml`。单个任务的当前状态、预算和交接信息位于对应的任务文件中。

> 注意：`config.yaml` 和本文件目前是流程协议，不会自己调用 Codex 工具。创建新上下文由当前 Codex 主控会话在阶段切换时调用应用层的线程工具完成；仓库中的 Python/React 代码不能直接创建 Codex 会话。

## 上下文调度

当前任务由主控上下文负责需求分析和最终验收。只有用户明确发出“进入开发阶段，创建新的开发上下文”后，主控上下文才可以把任务从 `planned` 推进到 `building`。主控上下文必须调用 `create_thread`，并把任务文件路径作为唯一交接入口。创建失败时必须保持 `planned`，不能假装已经切换。

```text
主控：inbox → spec → planned
  ↓ 用户明确确认 + create_thread 成功
开发：building → verifying
  ↓ 写回任务文件
主控：review → done
```

主控会话实际执行的工具动作是：

1. 读取任务文件，确认状态为 `planned`。
2. 等待用户明确发出：`进入开发阶段，创建新的开发上下文。`
3. 调用 Codex 的 `create_thread` 创建开发任务，并把任务文件路径放进初始提示。
4. 创建成功后，把返回的线程 ID 写入任务文件，再将状态改为 `building`。
5. 用 `wait_threads` 等待开发任务完成。
6. 读取开发任务写回的任务文件和代码改动。
7. 只有验证证据已写回后，主控上下文才能进入 `review`。

禁止事项：

- 不能仅因为任务文件写了 `new_context` 就假设新上下文已经创建。
- 不能在没有 `development_thread_id` 的情况下把状态改为 `building`。
- 不能把聊天里的口头计划当作线程创建成功的证据。
- 工具不可用、创建失败或状态不清楚时，必须暂停并报告，不得继续伪装成自动流程。

如果需要独立审查，只有用户明确要求创建审查上下文时，才可以用 `fork_thread`；如果需要给已经创建的任务补充指令，可以用 `send_message_to_thread`。这些动作发生在 Codex 应用层，不会出现在项目代码的 import 或脚本调用中。

上下文切换不复制完整聊天记录，只依赖以下共享记忆：

- `AGENTS.md`：项目规则
- `PROJECT_STATE.md`：项目整体状态
- `docs/loop/config.yaml`：Loop 配置
- 对应的 `docs/loop/tasks/*.md`：当前任务状态和交接内容

### 开发上下文交接提示

创建开发上下文时，使用以下约束：

```text
继续处理任务：<任务文件路径>

请先读取 AGENTS.md、PROJECT_STATE.md、docs/loop/config.yaml 和任务文件。
从任务文件记录的 planned 状态开始，只修改任务范围内的文件。
完成后把状态、改动文件、验证命令、验证结果和下一步写回任务文件。
不要正式发送外部通知。
```

### 停止条件

达到验证轮次、Token 或时间预算时暂停；连续两轮解决不了同一个问题时暂停；需求范围发生变化时回到 `spec`。暂停时必须在任务文件记录阻塞原因和需要用户决定的事项。

## 使用方式

1. 新需求先复制 `tasks/TEMPLATE.md`，放入 `tasks/`，状态设为 `inbox`。
2. 明确目标、验收标准和不做什么，状态改为 `spec`。
3. 确定涉及文件和验证方式，状态改为 `planned`。
4. 开发过程中更新实施清单，状态改为 `building`。
5. 完成后执行验证并记录结果，状态改为 `verifying`。
6. 交给需求提出人确认，状态改为 `review`。
7. 反馈处理完成后记录结果，状态改为 `done`。

## 状态说明

| 状态 | 含义 |
| --- | --- |
| `inbox` | 需求刚进入，尚未分析 |
| `spec` | 目标和验收标准已明确 |
| `planned` | 实施范围和验证方式已确定 |
| `building` | 正在修改代码或数据 |
| `verifying` | 正在执行自动检查和人工检查 |
| `review` | 等待需求提出人确认 |
| `done` | 反馈已处理，需求完成 |

## 原则

- 先明确验收标准，再开始写代码。
- 每次只做能验证的最小改动。
- 验证结果和用户反馈必须写回任务文件。
- 未通过人工确认的结果，不标记为 `done`。
